# 方案与实现

## 调用流程

```text
CLI 输入 → 逐项处理 → Agent 读取业务 Skill → 模型选择工具
                                         ↓
                       素材读取 / 审核 / 时段查询 / 草稿保存
                                         ↓
                         工具结果返回模型 → 继续或结束
```

AgentScope 2.0.11 的 `Agent`、`Toolkit`、`FunctionTool` 和 `OpenAIChatModel` 负责模型决策与工具调度；OpenCode Go 提供 `deepseek-v4.1-flash`。每项素材先读取 [排期 Skill](../skills/content-scheduling/SKILL.md)，读取失败或跳过时拒绝业务工具。模型可在工具返回后继续调用或结束；Skill 调用计入上限。

## 业务边界

- 保存前必须读取完整素材、审核通过并查询时段；保存事务重新核对占用情况。
- 素材共享一份排期，以完整日期与分钟判断冲突；待确认和已确认的有效草稿均占位。
- 替代时段标记为待确认，保留原要求；用户可通过 CLI 确认或取消，取消释放时段。
- 以素材 ID、要求时段和硬性标记识别业务请求；重复请求返回已有有效草稿，取消后重提创建新草稿。
- 保存结果由 SQLite 操作决定；不提供真实发布工具。

## 技术选型与取舍

### Python 与 CLI

项目使用 Python 3.11+ 实现，使用 uv 管理依赖和锁文件。评审可以通过 CLI 传入单条素材或 JSON 数组，直接获得结构化结果，再用同一个入口确认或取消草稿。项目提供 Mock、真实模型、测试和 Trace 导出命令，便于在本机复现。

方案讨论时也考虑过 HTTP API 和 Notebook。HTTP API 适合对接运营平台或其他服务；Notebook 适合交互式展示。当前交付以本机命令运行为主，CLI 可以覆盖输入、执行与验证的完整链路，部署和操作步骤较少。

### AgentScope 与业务 Skill

项目最初用原生模型工具调用循环打通流程，随后选用 AgentScope 2.0.11 组织 Agent、工具和 Skill。框架中的 `Agent` 负责模型决策循环，`Toolkit` 和 `FunctionTool` 注册素材读取、规则检查、时段查询及草稿保存工具，`OpenAIChatModel` 负责模型接入，`ReActConfig` 设置执行轮次上限。

模型先读取排期审核 Skill，再结合工具结果选择后续动作。例如，读取素材后发现信息缺失，可以停止并说明缺口；查询到时段冲突后，可以选择备选时段并保存待确认草稿。应用代码控制 Skill 读取顺序和工具调用上限，业务工具负责核对审核、时段及保存条件。

方案讨论中也考虑了 LangGraph 和 Google ADK。LangGraph 以状态、节点和边组织流程，适合需要显式编排复杂状态及中断恢复的场景；Google ADK 提供 Agent、工具和工作流能力。AgentScope 的工具注册和 Skill 加载方式与当前单 Agent 方案贴合，便于将业务指引、工具调用和运行记录串起来。

### 模型接入与离线运行

真实模型使用 OpenCode Go 的 `deepseek-v4.1-flash`，通过兼容接口返回工具调用。选择该模型主要基于现有账户可用性，以及项目对真实模型工具决策的需求；正常、冲突和失败场景的运行结果保存在 `examples/` 中。

项目同时提供离线 Mock 模型。它根据预设策略选择工具，使评审在没有模型密钥时也能运行素材读取、规则检查、时段查询和草稿保存流程。Mock 结果用于验证工程流程；真实模型记录用于观察模型在具体工具结果下的行动。

### SQLite 与草稿状态

草稿需要跨 CLI 调用保留，并支持确认、取消、重复提交和时段占用查询。项目选用 SQLite，将草稿持久化到本地文件，评审无需额外启动数据库服务。

保存草稿时，程序在写事务中查找已有有效请求、核对时段占用并写入草稿。相同请求返回已有草稿；取消草稿后释放时段，重新提交会创建新记录。业务请求由素材 ID、要求时段和硬性标记识别。若后续接入多人共享服务，需要结合部署方式评估集中存储、权限和操作审计。

### 单 Agent 与批量处理

本题的核心是让模型观察审核或时段结果后选择下一步。项目采用单 Agent，围绕四类业务工具完成一项素材的处理；批量输入按顺序逐项执行。这样前一项保存的草稿可以参与后一项的时段查询，每项也有独立的状态和 Trace。

用户对待确认草稿的确认与取消是明确的操作，由 CLI 调用业务功能直接完成。确认动作更新草稿状态；取消动作释放占用时段。

### DeepEval 与 OpenTelemetry

评测方面，项目使用 DeepEval 4.3.3 的 `BaseMetric` 实现确定性业务指标，检查 Skill 读取、任务状态和 SQLite 中的实际有效草稿。固定案例覆盖正常、冲突、信息缺失、规则风险、保存失败和重复提交；每个场景使用隔离数据。方案讨论中也考虑了支持 Agent 工具调用指标的 Ragas，当前使用 DeepEval 统一组织已有案例和结果。

追踪方面，业务 JSON Trace 保留步骤、工具参数、返回摘要和可获得的简要说明，供评审逐项核对；AgentScope 的 `TracingMiddleware` 结合 OpenTelemetry SDK 记录 Agent、模型和工具 spans，CLI 可将调用链导出为本地 JSONL。两类记录分别服务于业务验收和调用过程排查。

## 代码与技术取舍

`domain/` 定义业务请求身份和错误；`application/` 组织 Agent 与业务工具；`infrastructure/` 提供 SQLite、本地数据和模型接入；`presentation/` 提供 CLI；`composition.py` 装配依赖。SQLite 以写事务处理草稿去重与冲突核对，保留旧版草稿表记录。

业务 JSON Trace 记录动作、参数、工具结果和可获得的简要说明。`basis_source=model` 是模型主动输出的说明；`previous_tool_observation` 是程序记录的上一工具结果。AgentScope `TracingMiddleware` 可将模型、工具及 Agent spans 导出为 OpenTelemetry JSONL。

离线 Mock 是固定策略，适合检查流程。合成数据的候选时段固定，不自动跨日期搜索；项目未接入真实素材库、审核系统或发布日历。
